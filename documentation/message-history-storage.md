# Хранилище истории сообщений

На native-платформах история хранится в SQLite. Сообщения сохраняются с WAL
и `synchronous=FULL`: настройка энергосбережения не ослабляет подтверждение записи.

Для новой базы включается `auto_vacuum=INCREMENTAL` до настройки WAL и создания
таблиц. Этот режим позволяет существующему механизму обслуживания освобождать
страницы по явному запросу; он не означает полную перестройку после каждого
сообщения. Установка только в `onCreate` может оказаться слишком поздней для
уже инициализированного файла.

При открытии существующей базы её режим auto-vacuum сохраняется. Приложение
не запускает для этого автоматический `VACUUM`. В режиме `NONE` свободные
страницы после удаления остаются внутри файла и используются следующими
записями; отсутствие уменьшения файла само по себе не означает потерю данных.

Порядок и ограничения изменения auto-vacuum описаны в
[документации SQLite](https://www.sqlite.org/pragma.html#pragma_auto_vacuum).

Проверки создания базы и повторного открытия:
`test/storage/message_history_wal_test.dart`. Они используют временные файлы,
проверяют исходные WAL/FULL и сохранность строк; существующие данные пользователя
для тестирования не требуются.

Переключаемое сокращение перезаписи статистики доставки описано в
[энергосбережении](power-saving.md#сокращение-перезаписи-статистики-доставки).
Оно работает внутри одной транзакции и не меняет срок сохранения сообщений,
WAL/FULL или схему существующей базы.

## История CLI

Схема версии 3 добавляет две отдельные таблицы:

- `companion_cli_history`: ключ ноды, идентификатор операции, имя ноды, время,
  команда, ответ, статус и ошибка.
- `repeater_cli_history`: ключ ноды и репитера, идентификатор строки, их имена,
  время, тип строки и текст.

Поля хранятся обычными SQL-колонками, без JSON в CLI-таблицах. Составные ключи
и индексы отделяют историю разных источников. Старые таблицы сообщений и настроек
не перестраиваются; WAL/FULL сохраняются. Обновление со схемы 2 добавляет таблицы
CLI без удаления прежних строк. Нужная схема создаётся автоматически при открытии
БД, отдельную команду миграции вручную выполнять не требуется.

Переноса из экспериментального JSON-формата CompanionCLI нет: по решению
владельца эта невыпущенная версия не требует миграции истории. Новые записи
не используют `node_state` или SharedPreferences. В browser SQLite пока не
подключена основным хранилищем, поэтому история CLI временная и обозначена в UI.

Очистка выбранной консоли не очищает другие адреса или историю сообщений.
Общий порядок записей/удалений и ревизия адреса не позволяют старому async
callback восстановить удалённые записи, включая повторное открытие экрана.
Проверки: `test/storage/cli_history_database_baseline_test.dart`,
`test/storage/companion_cli_store_test.dart`,
`test/helpers/repeater_cli_history_test.dart`.


## Настройки контактов

В этой же БД таблица `contact_settings` хранит регион отправки и 11 локальных
параметров контакта: сжатие, его опции, транслитерацию, задержку отправки,
быстрые ответы и загрузку картинок по URL. Существующие значения автоматически
переносятся из preferences с удалением исходных ключей только после commit.
Используется существующая таблица схемы 3; отдельного обновления схемы не нужно.
[Полная структура и миграция](contact-settings-storage.md).
