# Разрешение сна CPU на Android

В **Энергосбережение → Свои настройки → Сон CPU (Android)** доступны два общих
режима и отдельные галочки BLE, TCP, companion-прокси и wardrive.
В готовых профилях CPU-настройки показаны без редактирования. Сохранённые свои значения не теряются
при выборе другого профиля или перезапуске приложения.

| Профиль | Сон CPU на Android |
|---|---|
| Выключено | Все CPU-разрешения выключены |
| Сбалансированный | Все CPU-разрешения выключены |
| Экономный | Только BLE-подключение в фоне |
| Максимальная экономия | «Всегда, когда возможно», с защитой операций |
| Свои настройки | Сохранённый выбор пользователя |

В «Экономном» одна BLE-галочка не разрешает сон для одновременно работающего
прокси или wardrive: каждый активный сценарий требует своего разрешения.
При TCP-подключении этот профиль сохраняет постоянное удержание. «Максимальная
экономия» применяет защищённый общий режим независимо от сценария и активности UI.
Обновление приложения применит эти значения и к уже выбранному готовому профилю;
сохранённые свои настройки не перезаписываются.

| Выбор | Когда разрешён сон | Наши удержания операций и worker |
|---|---|---|
| Отдельные сценарии | Только в фоне, если разрешены все активные сценарии | Сохраняются |
| «Всегда, когда возможно» | Независимо от сценария и активности приложения | Сохраняются |
| «Всегда, без исключений» | Независимо от сценария и активности приложения | Отключены |

**«Всегда, без исключений»** имеет приоритет над всеми остальными CPU-галочками.
Они становятся неактивными, но их значения сохраняются для возврата. Режим снимает
наш постоянный и временные CPU locks, включая запись/отправку, подготовку worker,
передачу управления и восстановление службы. Сон может задержать или прервать
незавершённую работу. Это не обещание снять locks Android и других компонентов.
Настройка выключена во всех готовых профилях и при чтении старых настроек.

«Всегда, когда возможно» делает четыре галочки сценариев неактивными, сохраняя
их значения. Без обоих общих режимов отдельные разрешения действуют только в фоне;
при сочетании функций
должны быть разрешены все активные сценарии. TCP включает восстановление ранее
установленного соединения. Галочка прокси относится к работающему серверу,
галочка wardrive — к запущенной записи покрытия, а не к открытому экрану карты.

Эти настройки управляют собственным CPU lock приложения. Android
определяет фактический сон. Фоновая служба, транспорт и GPS не выключаются,
Wi-Fi lock и системные ограничения батареи не меняются. На iOS группа скрыта
и на Immortalizer не влияет.

## Передача удержания и контроль связи

Плагин foreground_task не меняет уже взятый CPU lock через updateService.
Поэтому при первом применении политики в основном engine приложение сохраняет
признак управления и перезапускает worker службы с allowWakeLock=false.
Защищённый режим сначала готовит собственное удержание; «без исключений»
сразу запрещает его, в том числе для этой передачи. Основной Flutter engine и его транспорты
этой командой не останавливаются. Следующие изменения в той же сессии меняют
собственное удержание без повторного перезапуска worker.

После включения нового механизма возврат к «Выключено» восстанавливает постоянное
удержание собственным lock `mcoa:cpu-policy`; тег отличается от исходного lock
плагина. Managed watchdog при этом продолжает использовать uptime; возврат Off
восстанавливает постоянное удержание, но не возвращает старую реализацию worker.
При восстановлении службы без Activity защищённый механизм сначала
удерживает CPU до готовности worker и свежей политики основного engine.
Последний применённый безусловный режим сохраняется нативно: в нём старт worker
не возвращает удержание. Выбор Off при старте явно согласуется с native состоянием,
даже если там осталось прежнее безусловное разрешение. Возврат к защищённому режиму
учитывает уже выполняющиеся операции, без необходимости нового входящего события.
Отказ передачи удержания записывается в журнал PowerSaving; освобождение
CPU нельзя считать применённым только по положению галочки.

В защищённых режимах во время учтённой записи транспорта, teardown, сохранения истории, обработки
сообщений/кадров, активной отправки, передачи изображений, команды с ответом и
уведомления удержание сохраняется. Для run-операций обработчик ожидает применения
нативной политики перед входом в тело. Пассивные ожидания повторов не держат CPU;
сама выполняющаяся попытка держит. Существующие сроки и отмена операций сохранены.
В безусловном режиме CPU-подготовка перед run и подписка CPU-политики на операции
сняты; наблюдательный учёт продолжается. Возврат из режима восстанавливает защиту.
Реестр остаётся частичным: настройка не доказывает охват каждого стороннего plugin
callback, надёжность всех сценариев ещё требует аппаратной проверки.

Worker использует Android uptimeMillis, исключающий глубокий сон, и срок
20 секунд этого времени вместо календарного времени. Heartbeat содержит
поколение worker, сессию основного engine и возрастающий номер; старые, повторные
и слишком поздние сообщения не восстанавливают состояние. Repeat и heartbeat
остаются по 5 секунд; они не становятся будильниками и не гарантируют исполнение
во сне. После нативного repeat в защищённых режимах краткое удержание защищает
передачу управления worker и снимается после его проверки. В режиме «без исключений»
этого удержания нет; новый uptime watchdog при этом сохраняется.
Таймаут — индикатор жизнеспособности
основного engine, а не доказательство физического разрыва BLE.

## Проверки и пересборка

Новые строки добавлены только в ru/en ARB. Сначала владелец генерирует локализацию,
затем запускает один пакет без тяжёлых MCOimg:

```powershell
Set-Location O:\_git\meshcore-open
flutter gen-l10n
$cpuPolicyTests = @(
  'test/services/background_activity_baseline_test.dart'
  'test/services/background_cpu_diagnostic_test.dart'
  'test/services/background_heartbeat_sleep_baseline_test.dart'
  'test/helpers/background_work_tracker_test.dart'
  'test/models/power_saving_settings_test.dart'
  'test/screens/power_saving_screen_test.dart'
  'test/services/background_cpu_policy_test.dart'
  'test/helpers/background_cpu_work_test.dart'
  'test/helpers/cpu_sleep_binding_test.dart'
  'test/helpers/uptime_heartbeat_monitor_test.dart'
  'test/models/cpu_sleep_options_test.dart'
  'test/widgets/cpu_sleep_settings_card_test.dart'
  'test/connector/frame_work_tracking_test.dart'
  'test/connector/queued_message_work_tracking_test.dart'
  'test/storage/history_persistence_work_tracking_test.dart'
  'test/connector/retry_work_binding_test.dart'
)
if ($cpuPolicyTests.Count -ne 16) { throw 'Expected sixteen CPU policy files' }
flutter test @cpuPolicyTests --exclude-tags=slow --reporter expanded
flutter analyze
```

Старый диагностический режим проверяется отдельно из-за другого compile-time флага:

```powershell
flutter test test/services/background_cpu_diagnostic_test.dart --dart-define=MCO_DIAGNOSTIC_CPU_OFF=true --reporter expanded
```

Обычный публичный APK с новым нативным кодом:

```powershell
flutter build apk --release --split-per-abi --dart-define=MESHCORE_ENABLE_TRANSLATION=false
```

Для своей сборочной конфигурации используйте её штатную обёртку и учёт символов.
Hot reload не устанавливает новый Kotlin-код. Dart проверяет capabilities и не
принимает новый безусловный режим со старым adapter; нужен APK с новым Kotlin.
Отдельная пересборка Go-библиотек
для этой группы настроек не нужна. MCO_DIAGNOSTIC_CPU_OFF=true остаётся отдельным
статическим опытом с прежним heartbeat и имеет приоритет над рабочей политикой;
для её проверки он должен быть false. Это значение по умолчанию: отдельный CPU
флаг в обычной команде сборки не нужен.

## Аппаратная приёмка

Владелец проверяет доставку и отправку с погашенным экраном: BLE, TCP,
прокси, wardrive и используемые сочетания, затем возврат в приложение, переключение
«Свои настройки / Выключено», восстановление службы и остановку последнего
владельца. Отдельно проверить Android 9/API 28 и современный Android; minSdk
этим изменением не повышается. Flutter-тесты подменяют службу и нативный канал
и не подтверждают реальный handoff, suspend, периферийную BLE-рекламу или доставку.

Для режима «без исключений» проверить отсутствие собственного lock после
применения, во время операций, после повторных callback worker и восстановления
процесса без Activity. Затем выключить режим при незавершённой операции и проверить
возврат защиты. Отказ применения требует проверки журнала PowerSaving: если
плагин не удалось перезапустить, его прежний lock может остаться до успешной
повторной передачи. Не считать одно положение галочки доказательством release.

В dumpsys проверять собственный `mcoa:cpu-policy` и прежний lock плагина раздельно:
старый тег после перехода к новой политике уже не отражает всё удержание приложения.
Экономию нового рабочего механизма ещё нужно измерить. Первый диагностический
опыт не является приёмкой этой реализации или универсальной оценкой батареи.
