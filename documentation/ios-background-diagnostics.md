# Диагностика фонового режима iOS

Начиная с этой реализации приложение собирает счётчики кадров и снимки аудио
для исследования расхода фонового TCP. Сам режим удержания, формат тишины,
интервалы опроса и профили энергосбережения эта диагностика не меняет.
Минимальная iOS проекта остаётся 16.0.

## Как получить журнал

1. Включите журнал приложения перед опытом.
2. Подключитесь по TCP, оставьте разрешённым фоновый TCP и встроенное удержание.
3. Сверните приложение или заблокируйте экран. Для первого функционального
   снимка достаточно короткого окна; это ещё не замер энергии.
4. Вернитесь, откройте журнал приложения и нажмите существующую кнопку
   копирования. Она один раз запрашивает свежую диагностику, затем копирует
   журнал вместе с новой строкой. Старый Runner или ошибка запроса не мешают
   копированию; запрос ограничен тремя секундами.
5. Передайте строки `iOSExecutionStats`, `iOSFrameStats` и соседние
   `iOSRendering`/`iOSExecution`. Укажите длительность окна, выключался ли экран,
   работали ли приём/отправка и какой TCP-транспорт использовался.

Обычный TCP и встроенный Tailscale проверяйте отдельно. Во время будущего
сравнения энергии сохраняйте один профиль, сеть, фоновые функции и по
возможности близкую нагрузку. После обновления native-кода требуется полная
сборка приложения; hot reload её не заменяет.

## Счётчики кадров — `iOSFrameStats`

Сводка создаётся при закрытии и открытии presentation gate; покадрового лога
или отдельного таймера нет. Она также добавляется к снимку при копировании
журнала, если текущий binding поддерживает эти счётчики.

| Поле | Значение |
|---|---|
| `gateEpoch` | Номер окна закрытого gate в текущем Dart binding |
| `presentationAllowed` | Текущее разрешение presentation, не состояние TCP |
| `beginCallbacks` / `drawCallbacks` | Счётчики доставленных в binding callbacks с его создания |
| `warmUpCallbacks` | Подмножество begin callbacks без timestamp; не считать их обычными Vsync |
| `pipelinePasses` | Число вызовов `super.drawFrame`, не подтверждённые GPU submissions |
| `suppressedDraws` | Число draw callbacks, остановленных существующим guard |
| `gatedElapsedMs` | Монотонная длительность текущего/последнего закрытого окна; не CPU-время |
| `gatedBeginCallbacks`, `gatedDrawCallbacks`, `gatedSuppressedDraws`, `gatedWarmUpCallbacks` | Счётчики только текущего/последнего окна |

При возврате сводка сохраняет завершённое окно. Следующая деактивация, включая
Control Center, начинает новое; поэтому важны строки вокруг всего опыта.
Повторное одинаковое состояние не сбрасывает окно. Forced/warm-up callbacks
не доказывают, что дисплей непрерывно выдавал Vsync. Ноль callbacks тоже не
означает отсутствие сетевой, аудио- или другой CPU-работы.
Длительность берётся из Dart Stopwatch и не заменяет фактическое время опыта
или разность native UTC timestamps; по ней нельзя определять глубокий сон ОС.

## Аудио — `iOSExecutionStats`

Событийные снимки создаются при успешном старте/остановке плеера, его ошибке,
прерывании, сбросе media services и смене audio route. `source=requested`
обозначает явный снимок при копировании журнала. Запрос только читает состояние:
он не активирует audio session, не запускает плеер и не разрешает удержание.

| Поле | Значение |
|---|---|
| `eligible`, `manualAllowed`, `background`, `armed`, `legacyInjection` | Контекст контроллера в момент снимка |
| `running` | `AVAudioPlayer.isPlaying` в этот момент |
| `backendArmed`, `physicalBackground` | Фактические флаги ObjC backend; во время события старта/остановки контроллер ещё может завершать свой переход |
| `event` | Последнее диагностическое audio-событие; при запросе оно может быть прежним |
| `sampleRate`, `ioBufferDuration` | Фактические значения audio session; частота в Гц, buffer в секундах |
| `preferredSampleRate`, `preferredIOBufferDuration` | Предпочтительные значения; система может выбрать другие |
| `playerSampleRate`, `playerChannels`, `playerDuration`, `playerVolume` | Формат текущего player; duration в секундах; после освобождения player — нули |
| `startAttempts`, `playStarts` | Число попыток активации аудиопути и успешных `play` после установки backend в текущем процессе |
| `cleanupStops` | Вызовы cleanup существующего player/session, включая очистку после ошибки; не только нормальные остановки |
| `interruptions`, `mediaResets`, `routeChanges`, `failures` | Счётчики событий текущего процесса |
| `category`, `mode`, `categoryOptions`, `outputPortTypes` | Категория, режим, флаги и типы выходов; неизвестные текстовые значения заменяются на `other` |
| `nativeAtUtcMs`, `nativeUptimeMs`, `revision` | Native-время и отдельный порядок audio snapshots; они не управляют удержанием |

Для параметров работающего аудио смотрите прежде всего фоновое `event=started`
и последующие события в фоне. После возврата плеер штатно освобождён, а категория
может быть восстановлена — значения foreground-запроса не следует выдавать за
аппаратные параметры предыдущего фонового воспроизведения.

Новые диагностические строки не включают имена/UID аудиоустройств, IP,
аккаунты, auth URL, ключи или полный native map. Это ограничение новых строк,
не утверждение об отсутствии пользовательских данных во всём журнале.

## Ограничения

Эти данные показывают выполненную работу и настройки, но не расход в мА·ч и
не доказательство того, что система постоянно исполняла процесс. Успешные
unit-тесты не подтверждают фоновую доставку и отсутствие пропадающих символов
на конкретном iPhone. Реальный результат требует проверки владельцем.

Для будущего изменения audio buffer или планирования кадров будут отдельные
опции и проверки. В этой реализации экономия ещё не включалась.
