# Прикладные данные канала (GROUP_DATA)

[English version / Английская версия](CHANNEL_APP_DATA.md)

Этот документ — общая часть всех бинарных канальных форматов MCO Advanced: как
передаётся типизированная канальная датаграмма, какое прикладное пространство
она объявляет, как устроен конверт MCO Advanced в пространстве `0x0120`, какие
подтипы в нём есть и что делает приёмник с полезной нагрузкой, которую не умеет
читать. Тела внутри конверта заданы собственными документами и здесь намеренно
не повторяются:

- контейнер MCMP v3: [`MCMP_V3_PROTOCOL_RU.md`](MCMP_V3_PROTOCOL_RU.md)
- контейнер MCOtxt v1: [`MCOTXT_V1_PROTOCOL_RU.md`](MCOTXT_V1_PROTOCOL_RU.md)
- тело MCOimg v3: [`mcoimg_v3_reference_RU.md`](mcoimg_v3_reference_RU.md)
- тело MCOimg v4: [`mcoimg_v4_reference_RU.md`](mcoimg_v4_reference_RU.md)
- кадры компаньона, поле за полем: [`BLE_PROTOCOL.md`](BLE_PROTOCOL.md)

Эталоном для документа служит Dart-реализация из этого репозитория:

- `lib/helpers/channel_app_data_helper.dart` — конверт `0x0120`:
  идентификаторы, `encodeEnvelope`, `tryDecodeEnvelope`
- `lib/helpers/channel_binary_data_helper.dart` — порядок декодирования,
  унаследованные пространства, `tryDescribeUnknownAppData`, маркер
  `UnknownChannelAppData`
- `lib/connector/meshcore_protocol.dart` — `buildSendChannelDataFrame`,
  `parseChannelDataReceivedFrame`, `maxChannelDataLength`
- `lib/connector/meshcore_connector.dart` — `_handleIncomingChannelData`,
  `_addUnknownAppDataMessage`
- `lib/widgets/unknown_app_data_placeholder.dart` — текст заглушки
- `test/helpers/channel_binary_data_unknown_test.dart` — правила приёмника в
  виде тестов

## Соглашения

- Многобайтовые целые беззнаковые, little-endian.
- Текст — UTF-8.
- `varuint` — беззнаковое целое по основанию 128: каждый байт несёт семь бит
  значения, младшая группа первой, а установленный бит 7 означает, что следует
  ещё байт. Ноль — один нулевой байт. Эталонные декодеры принимают не более
  пяти байтов и отклоняют более длинное или усечённое значение.
- Идентификаторы записываются так, как их пишет реестр MeshCore: `0x0120`.

## Транспорт

Типизированная канальная датаграмма — пакет MeshCore с типом полезной
нагрузки `PAYLOAD_TYPE_GRP_DATA` (`0x06`), зашифрованный ключом канала точно
так же, как сообщение `GROUP_TEXT`. После расшифровки её содержимое таково:

| Поле | Размер | Значение |
|---|---:|---|
| `data_type` | 2 байта LE | прикладное пространство, см. ниже |
| `data_len` | 1 байт | число байтов в `application_data` |
| `application_data` | `data_len` байтов | прикладная полезная нагрузка |

`application_data` — не более 165 байт (`maxChannelDataLength`); прошивка
выводит тот же предел из размера полезной нагрузки пакета за вычетом одного
блока шифра и этого трёхбайтового заголовка. Принимающий узел отбрасывает
датаграмму короче трёх байтов или ту, у которой `data_len` больше, чем
следует за ним, а любую другую отдаёт клиенту как есть, каким бы ни был
`data_type`. Единственное исключение — узел South Edition с включённым
преобразованием MCOtxt, который отдаёт конверт MCOtxt приложению без этого
кодека обычным текстом; это описано в документе MCOtxt.

Между узлом-компаньоном и его клиентом датаграмма ходит в двух кадрах. Их поля,
включая упакованный байт пути, описаны в [`BLE_PROTOCOL.md`](BLE_PROTOCOL.md):

```text
CMD_SEND_CHANNEL_DATA (62 = 0x3E), клиент -> узел
[62][channel_idx][path_len][path...][data_type u16 LE][application_data]

RESP_CODE_CHANNEL_DATA_RECV (27 = 0x1B), узел -> клиент
[27][snr x 4, int8][2 резерв][channel_idx][path_len][data_type u16 LE][data_len][application_data]
```

В команде `path_len = 0xFF` запрашивает доставку флудом, и байты пути не
следуют; любое другое значение — длина маршрута, идущего следом. В команде нет
`data_len`: узел берёт `application_data` до конца кадра и записывает длину
сам. В ответе `path_len` — упакованный байт пути пакета, `0xFF`, если пакет
шёл без пути. При включённом RX-логе сырой пакет доходит до клиента и через
`PUSH_CODE_LOG_RX_DATA`; после расшифровки в нём виден тот же трёхбайтовый
заголовок.

## Пространства

`data_type` называет приложение, которому принадлежит датаграмма. Диапазоны
выделяются в
[`docs/number_allocations.md`](https://github.com/meshcore-dev/MeshCore/blob/main/docs/number_allocations.md)
MeshCore: проект пользуется диапазоном для разработки, пока строится, и
запрашивает собственное значение перед публикацией.

| `data_type` | Владелец | MCO Advanced при приёме |
|---|---|---|
| `0x0000`–`0x00FF` | зарезервировано MeshCore | игнорируется |
| `0x0100` | MeshCore Open | сохраняется заглушкой с именем пространства; раскладка не читается |
| `0x0110`–`0x011F` | Ripple | игнорируется |
| `0x0120` | **MCO Advanced** | конверт ниже |
| `0x0130`–`0x013F` | StreamSensor | игнорируется |
| прочие значения в `0x0100`–`0xFEFF` | запрашиваются pull request'ом в реестр | игнорируется |
| `0xFF00`–`0xFFFF` | разработка и proof of concept, запрос не нужен | игнорируется, кроме двух унаследованных значений ниже |

Два значения из диапазона для разработки старше выделения `0x0120` и
по-прежнему понимаются. Их полезная нагрузка — `senderNameLength(varuint) |
senderName | body`, без байта подтипа:

| `data_type` | Тело | Статус |
|---|---|---|
| `0xFFF0` | изображение MCOimg v1/v2, бинарная форма текста `im:` | по-прежнему отправляется для изображения `im:` при включённой бинарной отправке; по-прежнему декодируется |
| `0xFFF1` | текст, сжатый MCMP v2 | по-прежнему отправляется каналом с MCMP v2 при включённой бинарной отправке; по-прежнему декодируется |

Всё более новое идёт под `0x0120` с собственным подтипом. Бинарная отправка в
целом — настройка приложения «Отправлять расширенные данные бинарно (каналы)»
(`ChannelBinaryDataHelper.sendEnabled`); при выключенной каждый формат
возвращается к своему текстовому транспорту.

Ещё одно значение используется без строки в реестре: транспорт фрагментов
изображений (`lib/services/image_chunk_transport.dart`) объявляет `0xAE1C` для
фрагментов изображений AEIC. Коннектор предлагает принятую датаграмму этому
транспорту раньше пути конверта, только пока включены сообщения-изображения.

## Конверт MCO Advanced (`0x0120`)

`application_data` под `0x0120` таков:

| Поле | Размер | Значение |
|---|---:|---|
| `senderNameLength` | varuint | длина `senderName` в байтах UTF-8 |
| `senderName` | `senderNameLength` байтов | отображаемое имя отправителя в канале; может быть пустым |
| `subtypeVersion` | 1 байт | старший полубайт: id подтипа; младший: ревизия этого подтипа на проводе |
| `body` | оставшиеся байты | задаётся документом самого подтипа |

```text
data_type = 20 01            0x0120
data_len  = N
  senderNameLength (varuint)
  senderName (UTF-8)
  subtypeVersion (u8)
  body
```

`senderName` — внешнее имя отправителя канального сообщения, аналог префикса
`Name: ` в сообщении `GROUP_TEXT`: это то, что клиент показывает и что
привязывает проверка подписи. Подтип может оставить его пустым и нести имя
внутри тела, как делает MCOtxt; эталонный декодер показывает пустое внешнее имя
как `Unknown`, если тело не даёт своего.

Id подтипа и ревизия — каждый от `0` до `15`. Id называет формат; ревизия
меняется только тогда, когда тело меняется так, что прежний декодер не должен
за него браться, поэтому декодер выбирает разбор по паре. Ревизия считается
внутри своего подтипа: байт `0x20` — подтип MCMP `0x02` в ревизии `0x00`, а не
«MCMP v0».

Весь конверт, вместе с именем и телом, должен уместиться в `data_len`, поэтому
бюджет тела при данном имени равен
`165 - varuintLength(nameLength) - nameLength - 1`.

### Подтипы

| Подтип | Id | Ревизия | Байт | Тело | Спецификация |
|---|---:|---:|---:|---|---|
| MCOimg | `0x01` | `0x03` | `0x13` | MCOimg v3: packet nonce и сжатое изображение | [`mcoimg_v3_reference_RU.md`](mcoimg_v3_reference_RU.md) |
| MCOimg | `0x01` | `0x04` | `0x14` | тело MCOimg v4 | [`mcoimg_v4_reference_RU.md`](mcoimg_v4_reference_RU.md) |
| MCMP | `0x02` | `0x00` | `0x20` | контейнер MCMP v3: флаги, timestamp, опциональные отправитель, подпись и ссылка на ответ, сжатый текст | [`MCMP_V3_PROTOCOL_RU.md`](MCMP_V3_PROTOCOL_RU.md) |
| MCOtxt | `0x03` | `0x01` | `0x31` | контейнер MCOtxt v1; внешнее имя пусто, имя едет внутри | [`MCOTXT_V1_PROTOCOL_RU.md`](MCOTXT_V1_PROTOCOL_RU.md) |
| — | `0x04`–`0x0F` | | | не назначены | |

Новый формат берёт следующий свободный id в этой таблице и собственный
документ; несовместимое изменение тела берёт следующую ревизию своего подтипа.
В эталоне и то и другое живёт в `ChannelAppDataHelper` (`ChannelAppDataSubtype`
и константы `*Version`).

## Что делает приёмник

Правила ниже — те, которым следует MCO Advanced и которым ожидается
следование от другого клиента этих пространств, чтобы сообщения более нового
отправителя оставались видны как сообщения, а не исчезали.

Эталон декодирует каждую принятую датаграмму в таком порядке
(`_handleIncomingChannelData`):

1. транспорт фрагментов AEIC получает право первого отказа, пока включены
   сообщения-изображения (`0xAE1C`);
2. два унаследованных пространства `0xFFF0` и `0xFFF1` (`tryDecodeInbound`);
3. конверт `0x0120` (`tryDecodeAppData`) с диспетчеризацией по подтипу и
   ревизии;
4. всё, что осталось от пространства с известным владельцем
   (`tryDescribeUnknownAppData`), становится сообщением-заглушкой;
5. любой другой `data_type` игнорируется.

### Известный подтип, нечитаемое тело

Кодек первым сообщает о своей беде собственным текстом, потому что знает, что
именно не смог прочесть:

| Случай | Результат |
|---|---|
| MCOimg в ревизии, отличной от `0x03` и `0x04`, или тело v4, которое декодер отвергает как неподдерживаемый формат | заглушка «изображение не поддерживается» (`mcoimg-unsupported:<ревизия>` в хранилище), тело сохранено |
| MCOtxt в ревизии, отличной от `0x01` | текст MCOtxt о неподдерживаемой ревизии (`MCOtxtAppCodec.unsupportedFormatText`) |
| тело MCOtxt v1, которое не удалось раскодировать | текст MCOtxt об ошибке декодирования (`MCOtxtAppCodec.decodeFailedText`) |
| MCMP в ревизии, отличной от `0x00`, или тело, которое отвергает `McmpAppCodec.decodeBody` | MCMP об этом не сообщает: случай проваливается к заглушке ниже с именем подтипа `2` и ревизии |
| тело MCOimg известной ревизии, которое отвергает его декодер | проваливается так же, с именем подтипа `1` и ревизии |

Заглушка, таким образом, означает «эта сборка не смогла это прочесть», что
покрывает и формат новее сборки, и повреждённое тело; её формулировка потому и
говорит, что приложение, *возможно*, требует обновления.

### Незнакомый подтип или пространство с чужой раскладкой

Датаграмма из пространства с известным владельцем, которую ничто выше не
смогло прочесть, сохраняется, а не отбрасывается:

- Под `0x0120` конверт разбирается, насколько получится: внешнее имя
  отправителя, id подтипа и ревизия берутся, когда конверт корректен; полезная
  нагрузка, не являющаяся конвертом, оставляет только пространство.
- Под `0x0100` не читается ничего, раскладка принадлежит MeshCore Open.
  Называется только пространство.
- Сообщение сохраняется обычным канальным сообщением, текст которого — маркер,
  а `rawPayload` — весь `application_data`, чтобы более поздняя сборка,
  знающая формат, могла раскодировать его из истории. Маркер —
  `mcoapp-unknown:0x0120:<подтип>.<ревизия>` с десятичными id либо
  `mcoapp-unknown:0x0100`, когда добавить нечего
  (`UnknownChannelAppData.sentinelText` / `parseSentinel`).
- Экраны никогда не показывают маркер. `unknownAppDataPlaceholderText`
  превращает его в локализованную строку: *Получен пакет неизвестного подтипа
  (0x0120 MCO Advanced, подтип 3 версия 2); возможно, требуется обновить
  приложение* либо *Получен пакет в формате, который это приложение не умеет
  читать (0x0100 MeshCore Open); возможно, требуется обновить приложение*,
  когда известно только пространство. Она появляется в пузыре, в цитате
  ответа, в баннере ответа и в превью списка каналов; поиск по сообщениям,
  работающий без локализации, показывает сам маркер.
- Имя отправителя — внешнее имя конверта, если оно прочитано, иначе `Unknown`.
  Число хопов, ширина хеша и SNR кадра сохраняются, как у любого сообщения.
- Уведомление не поднимается; счётчика непрочитанных достаточно.
- Копия такого пакета из RX-лога игнорируется: узел отдаёт каждую датаграмму и
  кадром тоже, так что ничего не теряется, а маршрут не подмешивается в
  сообщение, которое никто не может прочесть.

### Правила для другой реализации

- Декодировать по паре «подтип, ревизия»; никогда не отдавать тело одной
  ревизии декодеру другой.
- Сохранять конверт с незнакомым подтипом или ревизией, показывать заглушку с
  именем пространства, подтипа и ревизии и хранить полезную нагрузку.
- Считать `0x0100` пространством MeshCore Open: показывать или игнорировать,
  но не разбирать как этот конверт.
- Игнорировать любой другой `data_type` либо обрабатывать как свой, если он
  ваш.
- При отправке пользоваться своим пространством. Новый формат под `0x0120`
  берёт новый подтип из таблицы выше; несовместимое изменение тела берёт новую
  ревизию своего подтипа.

- **MCO Advanced** (этот репозиторий): файлы, перечисленные в начале. Правила
  заглушек закреплены тестами
  `test/helpers/channel_binary_data_unknown_test.dart`.

  `src/helpers/mcotxt/MCOtxtTransport.h` каждый опознают конверт `0x0120` по

  который узел перекодирует от имени приложения.
